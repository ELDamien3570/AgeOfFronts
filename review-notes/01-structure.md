## How it works today

**Runtime topology.** One `Skirmish` class (`src/skirmish/Simulation.ts`, 5617 lines, 178 methods, 98 value imports) is the authoritative match. It is hosted in three places with no code difference: (1) the browser Web Worker `src/skirmish/worker.ts` for solo play and local diagnostic replays (`worker.ts:113-117` restores a `DiagnosticReplay` checkpoint), (2) the Node `ReservedMatchWorker` thread for online matches (`multiplayer/infrastructure/serverMatchWorker.ts:155`, `:177`), and (3) `client/lab/BattleLabModel.ts` on the main thread for the balance lab. Online clients only run `client/multiplayerStateWorker.ts` (decode) and `OnlineMatchSession.ts`. The server loop is: coordinator posts `advance {commands, ticks, disconnectedPlayerIds}` → worker flips disconnected seats to AI via `setAiController` (`serverMatchWorker.ts:259-262`) → `commandApplications.apply` per command → `match.step()` × ticks → optional snapshot capture through `SnapshotEncoder` + a separate encoding worker + `PublicationQueue`. The server never calls `checkpoint()`/`restore()` (CONFIRMED by grep of `multiplayer/infrastructure`); checkpoints exist only for the local replay path and the dead host-election path (below).

**Tick.** `Skirmish.step()` (`Simulation.ts:3368`) wraps `performTick` (`:3378-3667`) in per-tick permission caches. `performTick` order: queued-leg deadlines → path warming → volley expiry → construction countdown → `promoteTribes` → `expansion.beforeStep()` (progression, automatic tiers, diplomacy, fortifications, trenches, supply, refits/enlargements, economy directors, `thinkProgression`) → diplomatic withdrawal → reserves → `thinkAi()` → ship movement + raid diplomacy → engagements/armies → route draining (24 jobs/tick) → cavalry/column travel → held-unit index → attack-approach index → per-squad navigation intents → formation locomotion → `LocalAvoidance.step` with a transport-proposal/column-trail commit callback → fortification/entry rollback → raid-entry war declarations → navigation advance → formation states → `fight()` → `fightShips()` → `expansion.afterMovement()` → orphan cleanup → replenish → `capture()` → coastal/absorption ownership → warships → recruitment → `checkWinner()` → armies reconcile. The 125 ms budget is shared by everything; nothing is time-sliced across ticks except route work and a few AI directors' work units.

**Layers (as found).** `src/skirmish/*.ts` root = movement/pathing/spatial/terrain/map generation + `Simulation.ts`, `Protocol.ts`, `Rules.ts`, `FactionRules.ts`, codecs. `domain/*` = gameplay services (Expansion aggregate, Battle, Armies, Trade, Supply, Diplomacy, Fortifications, ~40 `Ai*` modules) that reach the world only through interfaces (`ExpansionWorld` at `domain/Expansion.ts:103-145`, `BattleWorld` at `domain/Battle.ts:72`, `ArmyWorld` at `domain/Armies.ts:46`, `TradeWorld` at `domain/Trade.ts:38`). `content/*` = balance tables and compiled JSON, validated and hashed by `content/Catalog.ts`. `multiplayer/*` = coordinator (`CoordinatorServer`, `RoomCoordinator`, `LiveMatch`), worker infrastructure, wire codecs. `client/*` = renderer/HUD/view models (`main.ts` 2177 lines, `Renderer.ts` 2479 lines). `lobby/*`, `planning/*` = lobby settings and dev planning pages.

**Dependency directions (measured, value+type imports, 453 files).** domain→domain 414, root→root 296, client→client 263, domain→root 227, client→root 162, domain→content 126, client→domain 124, root→domain 105, client→content 83, content→domain 32, content→root 27, root→content 26. Zero imports of `Simulation.ts` from `domain/`, `content/` or `client/` other than `client/lab/BattleLabModel.ts`; the only importers are `worker.ts`, `serverMatchWorker.ts`, `HostedRuntime.ts`, `CommitVerifier.ts`, `DiagnosticReplay.ts`, `BattleLabModel.ts`. One real value-import cycle: `domain/AiNavalBombardment.ts:5` ↔ `domain/AiNavalPlanner.ts:5`. One upward import: `Simulation.ts:33` → `lobby/FactionPalette`. Highest fan-in: `Protocol.ts` 161, `domain/Definitions.ts` 71, `content/Units.ts` 47, `domain/FormationGeometry.ts` 39, `domain/Manpower.ts` 31, `Rules.ts` 26.

**Rulesets.** `MatchOptions.ruleset === "ages-v1"` creates `Expansion` (`Simulation.ts:1004-1012`). Every production entry hard-codes it: `client/main.ts:673`, `:708`, `multiplayer/application/LiveMatch.ts:157`. Without it the match runs the original three-class sandbox driven by `Rules.ts` (`SQUAD_RULES` `:7`, `SHIP_RULES` `:218`, `STARTING_GOLD`, archer charge constants) with its own `developAi`/`developTribeAi` (`Simulation.ts:5253-5343`) and `fight()` using `SQUAD_RULES[squad.kind]` (`:4470`). `Rules.ts` also holds `BUILDING_RULES`, which *is* live: it is the building catalogue for both rulesets, imported by 26 files including `content/Buildings.ts:2`, `content/Catalog.ts:8` and `multiplayer/CommandSchema.ts:4`.

**Versions and hashes.** `content/Catalog.ts:96` computes `CONTENT_HASH` (FNV-1a over units/techs/buildings/… plus hand-bumped `combatRevision: 10`, `navalAutonomyRevision: 3`, etc.) and `validateCatalog()` runs at import. Checkpoints carry `version: 11 as const` (`Simulation.ts:241`) and `restore` checks dimensions and `JSON.stringify(options)` (`:249-251`) but not `CONTENT_HASH`. Packet detail layouts keep versions 1–5 with legacy stride branches (`SnapshotDetails.ts:418`, `:486`, `:521`, `:598`).

**Tests.** 360 `*.test.ts` under `tests/skirmish` (plus 18 benchmark/profile `.ts`, 8 diagnostics `.json`, one `.md`), run via `vitest --config vite.skirmish.config.ts` (node environment, no setup file). 190 test files construct a real `Skirmish` on a `GameMapImpl`; only 7 use `vi.mock`. There is no `.github/` and no `.husky/` in the checkout (despite `"prepare": "husky"`), so nothing gates commits; `scripts/pr-gate` and `scripts/issue-lifecycle` are GitHub Action sources without workflows here.

**Inherited OpenFront.** `src/core` (49.6k lines), `src/client` (118.9k), `src/server` (12.4k) remain in the repo. The skirmish code imports only `core/game/GameMap` (`GameMapImpl` + type), `core/game/Game` (`TerrainType` enum) and `core/PseudoRandom` (CONFIRMED by grep; built chunks contain no `RailNetwork`/`AllPlayersStats`/`formatPlayerDisplayName` symbols, so tree shaking drops the rest). ## Strengths

- **Dependency direction is genuinely one-way at the hard boundary.** No `domain/`, `content/` or `client/` module imports `Simulation.ts`; domain services get the world through narrow-ish interfaces and are constructed by `Expansion` (`domain/Expansion.ts:206-257`). This is the single most valuable property to protect during any refactor.
- **Entity ownership is centralised.** `EntityCollection` (`EntityCollection.ts`) is the only writer; indexes (`UnitIndex`, `BuildingIndex`, change journals) are derived hooks (`Simulation.ts:370-400`). Replication reads journals rather than diffing (`:5561-5573`).
- **The simulation is host-agnostic.** The same class runs in the browser worker, the server worker and the lab; `onPhase` diagnostics are the only wall-clock dependency inside `Simulation.ts` (`:212`).
- **Content is validated and fingerprinted at load** (`content/Catalog.ts:51-80`, `:96`), and client/server compatibility is enforced by a source hash rather than trust.
- **Tests exercise the real simulation**, not mocks, and the suite is large, fast per file and parallel. Checkpoint round-trip equality is asserted in several places (e.g. `tests/skirmish/FlexibleFrontage.test.ts:182`).
- **Command validation is layered sensibly**: transport shape (`multiplayer/CommandSchema.ts`), pure policy (`domain/CommandPolicy.ts`), then domain legality inside `applyCommand`/`Expansion.command`.

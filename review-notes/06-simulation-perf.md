## How it works today

### Clock and scheduling
`TICKS_PER_SECOND = 8` (`Protocol.ts:18`), `TICK_MS = 125`. `LiveMatch.ts:714–736` advances **exactly one tick per coordinator request** (`ticks = 1`), computes clock debt `due`, and when debt exceeds `MAX_ADVANCE_TICKS` it rebases `nextTickAt` so at most ~4 ticks of debt are kept ("slow down, don't catch up"). Background snapshots are gated to 200 wall ms **and** 200 simulated ms, so under overload publication slows with the sim. The worker runs with `maxOldGenerationSizeMb: 384` (`ReservedMatchWorker.ts:22`). There is no catch-up burst; a 300 ms tick simply delays everything by 175 ms.

### Caches: revision-keyed vs rebuilt wholesale
Revision-keyed (good): `movementLand` list (membership/cargo revision) and `spatial` grid (spatialRevision) 474–489; `PhaseSpatialViews` (squad/ship spatialRevision) for combat/trade; `routingObstacleRevision` strings keyed by (policy, fortification version, alliances) 672–697; `aiFootprintAllowed` per-tick cache fenced by operations/diplomacy/threat revisions 553–560; `captureContributions` rows keyed by position/pose/owner/`environment:permission` key with dirty bits from `invalidateCapture` 4621–4629; `attackApproaches.cache` by signature; `HierarchicalPaths.startTrees` by cluster revision (LRU 512, `START_TREE_CACHE`, HierarchicalPaths.ts:9); `TilePaths.routes` by cost revision (16 384 entries / 2 M tiles); `columnCertificates`, `routeSuffixLengths`, `settledMotions` as WeakMaps keyed by immutable containers; `moveContinuations` keyed by order revision + JSON of next order + obstacle revision.

Rebuilt wholesale every tick: `heldSpatial` (3456), `attackApproaches.slots/loads` + the `targets` Map of all squads (AttackApproaches.ts:60–71), `LocalAvoidance.active` sort (232–236), `Battle` sorted alive list (648–649), `fightShips` sorted ships (2753), `thinkAi` per-player army arrays (4869–4875), `checkWinner` sets (5428–5432), `capture()` `defenses` set and per-squad key strings, `navalSpatial` (when phase views not used), `CrowdRecovery` lease filtering, `PassageTraffic.coordinate` queues (if called — it is not called from `performTick`; see Open questions).

### Route budget behaviour
- `RouteWork` (synchronous repairs): 60 units/tick at 8 Hz (`480/TICKS_PER_SECOND`, 604; the comment at 491 still says 24). FIFO with a 2:1 human:AI turn when any human task is pending; effort cut-off `ROUTE_EFFORT_LIMIT = 20 000` read from **`this.paths.work` only** (land graph) — amphibious-graph `findExact` and `LocalDetours` work are invisible to it (Issue 1).
- `RoutePlanner` (resumable exact/corridor search): 10 240 work units/tick in 64-unit quanta (`81920/TICKS_PER_SECOND`, 612), 128-job queue, 65 536-slot arena. Fairness: per quantum `selectJob` scans all jobs (365–420), then `nextJob` (423–490) does a 2:1 interactive/background turn, a 3:1 committed-cargo/fresh background turn, and round-robins **by player id then by caller**. Admission backpressure in `request` (492–535): background requests are refused at 120 jobs, uncommitted background at 104; refused requests return `false` and the caller retries next tick.
- `MovementAdmission.step` (680–712): intents ≤32, then 2/3 of the budget to human admissions, remainder round-robin; `stepAdmissions` 800–1066 rotates admissions and **spends one budget unit per refused planner request** ("routes" phase 925–945), so when the planner is full the admission budget is burned on rejected `request` calls every tick (match-259: 98.65 % of 50 507 requests rejected in 600 ticks; my probe shows 106–113 planner jobs with 167–326 admissions waiting).
- Humans first: yes at three levels (RouteWork priority turn, `stepInteractive` extra allowance + 8 reserved planner slots, `priorityOf` turn in `nextJob`). AI fairness is by player then caller, so 44 AIs each get ≈1/44 of the background turn; **starvation shows up as deadline rejections** (`autonomousRouteDeadlineTicks`, planner 547–572; admissions 681–693), not as unbounded queueing. A deadline-rejected AI admission is re-issued by the AI on its next think, which is the retry storm the 259 profile documented.

### Movement work vs moving squads
Work is proportional to **all land squads** for: navigation (17), formation locomotion unless settled (18), swept guard query + `apply` (20), rollback guard (21), `advanceNavigation` (23), formation states (25), capture row check (32), combat ledger walk (26), `checkWinner` (37). Only the ORCA/heading sampling, friendly spacing and clearance callback are proportional to moving squads. The `settledFormationLocomotion` WeakMap (FormationLocomotion.ts:27–45) is the only "sleeping squad" mechanism and it only removes the locomotion allocation.

### Capture
`capture()` cost per tick = O(B) for the defensive key sweep + O(S) row validation + O(29) per refreshed row (moved squad) + O(activeClaims). Sparse clearing is good: `CapturePressure` keeps persistent counted contributions (retain/withdraw) and only `activeClaims` are visited; a fully-owned footprint with no acceleration/fallout skips its tile loop (`ownedSkipped`). The ARM handoff measured capture at ~5–7 ms with ~580 owned-skip rows; my probe shows 3–5 ms at S≈1000 with ~900 reused rows. The cache is invalidated wholesale whenever `paths.revision` (forest cost epoch) or the alliance list changes because both are baked into `environment` (4662–4663).

### Winner/elimination
`checkWinner` is O(S+B+F) with four allocations every tick (5428–5432). Elimination itself is O(T_victim log T_victim) (sorted tile list, 5465–5471) with `changeOwner` per tile — each `changeOwner` does `invalidateCapture` (49 cells), a `new Set(neighbors…)` (4834), supply/operations/adjacency/absorption/coastal/placement notifications, a building scan, and for captured hostile buildings an O(S log S) `squads.filter().sort()` (4851–4858). A large faction's elimination is a single-tick spike of tens of thousands of such calls (Issue 7).

### Memory
Entity records are plain objects created once by `structuredClone` in `EntityCollection.add` and mutated in place through `Object.assign`/direct property writes (EntityCollection.ts:48–66); optional fields (`locomotion`, `formation`, `movementStatus`, `charge`, `aiWithdrawal`, …) are added lazily, so squad hidden classes **diverge by which optional fields a squad has ever received** (Issue 10). Positions are integers (`Math.round` in avoidance/locomotion); `previousPositions` is a Float64Array; `CapturePressure`, `PlanningWorkspace`, path cost/parent arrays, `HierarchicalPaths` trees, `CombatActivity` epochs are typed arrays. Bounded containers: route cache (16 384 / 2 M tiles), start trees (512), journals (65 536 tiles / 32 768 entities, `LatestChangeIndex` evicts oldest), `captureFootprints` (max(1024, 2S)), admission events (128), `HomeTerritory.failures` (2048). Growth-only Maps are all keyed by player id or are local to a call (scan in notes; nothing per-squad grows without pruning: `removeSquad` hook 384–392 deletes navigation/detour/revision/leg/continuation/approach state; `movementClearance` is pruned in `removeSquad` 1222; `captureContributions` via the `seen` pass; `LocalAvoidance.previous/motion` and `CrowdRecovery.waiting` prune every step).

### Determinism inside the hot loop
All per-tick orderings I checked are id-sorted or insertion-ordered Maps with deterministic mutation history; every `sort` in the hot paths has an id tiebreak (`LocalAvoidance` 236, `CrowdRecovery` 109–113, `PassageTraffic` 146–150, `HomeTerritory` 97–101, `changeOwner` 4854–4857, `ownedLandNearest`). `Math.atan2/sin/cos/hypot` produce floating headings stored in `locomotion` and `formation.facing`-derived values; V8 uses its own fdlibm port so this is deterministic across x86/ARM for the same V8 version, but the handoffs explicitly note cross-architecture hashes were never compared. `attackApproaches` signatures and `CrowdRecovery` centres use float arithmetic but only feed rounded outputs. No `Math.random`, no `Date`, no wall-clock in the sim path (`performance.now` only under `onPhase`).

## Strengths
- Phase boundaries are explicit and instrumented (`diagnosticPhase`), and every budget is a deterministic counter (route work, planner quanta, admission units, column decisions, neutral scans, engagement detection) — no wall-clock inside the sim.
- Spatial indexing is good: bitset-occupied `SpatialGrid` with partition-exclusion, extent-aware overlap queries, reused result arrays; `PhaseSpatialViews` shares rebuilds across combat/trade by revision; `movementLand` avoids redundant sorting.
- The planner is a serious piece of engineering: one shared arena, resumable exact/corridor/water-shortcut search, charged reclamation, checkpointable scheduler state, player/caller round-robin, interactive reservation, committed-cargo protection, deadline semantics separated from capacity.
- Capture is incremental with persistent counted pressure and sparse claim visiting; the owned-footprint skip and dirty-bit invalidation through `changeOwner` are the right design.
- Movement reuses scratch aggressively (`MotionScratch` rows, obstacle pool, `previousPositions`, clearance proofs, settled-locomotion WeakMap) and the swept-collision guard runs only against hostile partitions.
- Entity removal is centralised (`squadEntities` hooks) so most per-squad side tables cannot leak; checkpoint/restore clears derived caches and rebuilds ownership sets from `owners`.

## Issues

### 1. Synchronous route repair/detour work is unbounded by the effort limiter (p99 spike source)
- **Where**: `Simulation.ts:601–608` (`routeWork.drain(480/TICKS_PER_SECOND, {read: () => this.paths.work, limit: ROUTE_EFFORT_LIMIT})`), `Simulation.ts:4064–4115` (`repairNavigation`), `LocalDetours.ts:23–155`, `Pathfinding.ts:349–409` (`findExact`).
- **Severity**: high. **Confidence**: CONFIRMED mechanism, SUSPECT magnitude.
- **Mechanism**: `RouteWork.drain` executes up to 60 navigation tasks per tick synchronously. A `repair` task first runs `LocalDetours.find`: it allocates a `Float64Array`/`Int32Array`/`Uint8Array` lattice at FIXED/8 resolution over the bounding box (+2 FIXED) and A*-expands up to **6 000 nodes**, each expansion testing 8 neighbours with `clear()` = `clearLeg` (movement policy + fortification sweep) + `traversable` + a scan of every held squad within 10 FIXED (`fixed.every`). None of that is counted in `this.paths.work`. If the detour fails it then calls `squadPaths(playerId).findExact(..., 2048)`; for amphibious factions that is `amphibiousPaths.work`, also not read by the limiter (`this.paths.work` is the land graph only). `recoverNavigation` (3994–4036) queues a repair once per second per stalled move squad, so in a jam of 100–300 stalled squads 12–40 repairs land in every tick.
- **Consequence**: single ticks of 100 ms+ in the "routing" phase (my probe: routing max 98 ms at S≈1000 with no human orders; ARM qualification p99 255 ms). The `ROUTE_EFFORT_LIMIT` guard gives a false sense of boundedness.
- **Repro sketch**: 200 squads ordered through a one-tile gap held by hostile squads on hold; watch `onPhase("routing")` — each second a burst of repairs arrives (ids staggered by `progress.recovery`).

### 2. Admission budget is burned on refused planner requests; AI admissions starve by deadline, not by queueing
- **Where**: `MovementAdmission.ts:925–945` (`member.requested = this.ports.request(...)`; `used++` regardless of result), `RoutePlanner.ts:507–517` (refuse at 120/104 jobs), `Simulation.ts:613–626` (budgets), `MovementAdmission.ts:681–693` and `RoutePlanner.ts:547–572` (deadline rejections).
- **Severity**: high at 52 factions. **Confidence**: CONFIRMED (code) + evidence (match-259: 49 824/50 507 requests refused; my probe: planner pending 106–113 vs 128 cap, 167–326 admissions pending).
- **Mechanism**: every admission in the `routes` phase attempts `routePlanner.request` each time it is visited; when the queue is at the background cap the request is refused and the admission is re-queued with `requested=false`, consuming one unit of the 80–320-unit land budget per attempt and allocating a request context + obstacle-revision string each time. With 44 AIs the queue is permanently full, so most of the admission budget is spent on refusals, and admissions that never get a slot before `autonomousRouteDeadlineTicks` are rejected with `ROUTE_CAPACITY_REASON`, which the AI answers with a fresh think and a fresh admission.
- **Consequence**: wasted CPU each tick (the 259 profile attributes 24.7 % of sampled time to `drainRouteBatch`), AI armies that visibly dither, and human orders that are protected only by the 8 reserved slots — a human mass order of 30 squads is split into 10-squad cohorts (`MovementAdmission.ts:429`) and needs 3+ planner slots, which can exceed the reservation when 44 AIs keep the queue full.

### 3. AI phase does an O(frontier) `aiFootprintAllowed` scan per AI player per tick
- **Where**: `Simulation.ts:4970–4976` (`homeNeedsLand = frontier.some(tile => owners[tile]!==player.id && (...) && this.aiFootprintAllowed(player.id, tile) && this.map.euclideanDistSquared(player.base, tile) <= homeRadius ** 2)`), reached whenever the per-player `continue` at 4949–4951 does not fire (any squad due; with interval 6 ticks and ≥6 squads that is nearly every tick).
- **Severity**: medium (grows with F_ai × empire size). **Confidence**: CONFIRMED.
- **Mechanism**: `frontier` is sorted by distance from base (HomeTerritory.ts:97–101). `some` stops at the first eligible tile, but the common mid/late-game case (home radius fully owned, frontier of thousands of tiles) evaluates `aiFootprintAllowed` (a 29-cell scan on cache miss; cached per tick per owner/tile) on **every** frontier tile before the cheap distance check rejects it. 44 AIs × a few thousand frontier tiles per tick.
- **Consequence**: my probe's "ai" phase grows 3.4 → 9.2 ms mean (max 125 ms) with no human input; on ARM ×2.4. Trivial fix: check distance first and `break` once `euclideanDistSquared(base, tile) > homeRadius²` (the list is sorted by that key).

### 4. Combat ledger resolution does O(S) `damageManpower` allocations and four extra O(S) passes every tick
- **Where**: `Simulation.ts:4554–4607` (`resolveLandDamage`): 4586–4592 call `damageManpower(squad, Math.round(dealt*HEALTH_SCALE))` for every manpower squad even when `dealt === 0` (Manpower.ts:97–122 always allocates a new `manpower` object), then `recordSoldierCasualties` (computes `manpowerCount` before its `deaths <= 0` return), `syncFormationCounts(this.squads)`, `this.squads.filter(...)`, `[...this.squads].reverse()`.
- **Severity**: medium. **Confidence**: CONFIRMED.
- **Consequence**: at S = 1 500 that is ~1 500 short-lived objects and ~6 000 iterations per tick purely to discover nothing happened; GC share (7.9 % in the live profile) and the constant ~10–13 ms combat floor in my probe. Guard with `if (dealt) {...}` and iterate `damage` keys instead of all squads.

### 5. Movement is O(S) in several places that should be O(S_moving)
- **Where**: `Simulation.ts:3481–3488` (navigation for every land squad), `3571–3598` (rollback guard: stationary squads have no clearance proof, so they take the full `fortifications.clearMovement` + `aiFootprintAllowed` path every tick), `LocalAvoidance.ts:519–552` (swept guard `grid.query` for every active squad), `Simulation.ts:3521–3569` (`apply` → `{...changes, ...locomotion}` + `updateOwned` per squad), `3609–3616` (`advanceNavigation` for every squad, with `JSON.stringify` per tick for free-travel squads holding a queued move, 3873).
- **Severity**: medium-high (this is the ~45 % movement share). **Confidence**: CONFIRMED by reading; the ARM handoff measured movement ≈ 23 ms at S≈725 and my probe 36 ms at S≈1000 → ≈0.035 ms per squad per tick regardless of activity.
- **Consequence**: an idle garrison costs the same as a marching army. The qualification fixture is mostly garrisons.

### 6. Planner `step()` allocates and rescans the whole job table several times per tick
- **Where**: `RoutePlanner.ts:547` (`[...this.jobs.values()]` deadline sweep), `574–578` (three more `[...jobs.values()].filter().flatMap()` for `pinSharedPreparation`), `579–582` (`humanWaiting` spread + `some`), `365–372` (`selectJob` pushes every job into scratch per quantum → 160 quanta × 128 jobs at 8 Hz), `680–690` ("active background" count loop per quantum when a fresh search is selected).
- **Severity**: low-medium. **Confidence**: CONFIRMED (profile: `selectJob` 5.8 % of sampled time at 20 Hz; at 8 Hz the per-tick budget is 2.5× larger so quanta per tick rose from 64 to 160).
- **Consequence**: ~20–40 k job visits per tick before any search work; fixable by keeping per-class counters (interactive/background/committed/active) updated on insert/complete and by deferring the deadline sweep to once per second.

### 7. Elimination and large ownership transfers are single-tick O(T_victim × (49 + notifications + B)) spikes
- **Where**: `Simulation.ts:5465–5471` (per-tile `changeOwner` loop), `4813–4865` (`changeOwner`: `invalidateCapture` 49 cells, `routeFootprints.clear()` 4830, `new Set(neighbors…)` 4834, `buildingIndex.at`, captor `squads.filter().sort()` 4851–4858, `this.buildings.some` per former owner 4860–4864).
- **Severity**: medium (rare but guaranteed tail). **Confidence**: CONFIRMED mechanism; magnitude SUSPECT (a 5 000-tile faction ≈ 250 k cell visits + 5 000 Set allocations + per-tile domain notifications).
- **Consequence**: the "cleanup" phase is normally <1 ms but an elimination of a large AI (expected regularly with 44 AIs) will produce a one-off tick of hundreds of ms. Same shape for `nuclearBlast` and `territoryAbsorption` pockets. Note also `this.routeFootprints?.clear()` on **every** `changeOwner` invalidates the whole per-tick permission cache, so a tick with many captures repeatedly re-derives `aiFootprintAllowed` for later phases.

### 8. `stepWarships` scans all buildings per repairing ship
- **Where**: `Simulation.ts:3212–3218`, `3261–3267` (`this.buildings.find(b => b.id === ship.repairPortId && ...)`).
- **Severity**: low. **Confidence**: CONFIRMED.
- **Consequence**: O(H_repair × B); with 300 warships and 800–900 buildings (match-259 had 861–904) and a naval war this is 10–50 k comparisons per tick. `this.building(id)` is O(1) and already exists (1227).

### 9. Capture row cache is invalidated globally by any forest-cost change or alliance change
- **Where**: `Simulation.ts:4662–4663` (`environment` = `paths.revision : fortifications.version : alliances`), `4677` (`key` per squad), `4680–4683` (row refresh when key differs); `PathTopology.ts:49–53` bumps the cost revision on any forest change; `Simulation.ts:1077`/`1105` (`forestOf(map).occupy` on every building placement).
- **Severity**: low-medium. **Confidence**: CONFIRMED.
- **Consequence**: every building placed on forest by any of 52 factions forces all S rows through `captureQuery` + footprint filter + diff next tick (`captureWork.refreshed = S`); my probe shows windows with 384–563 refreshes and `reused = 0`. Forest cost epochs do not change walkability or capture eligibility (`captureQuery` depends on fortifications and permissions only), so `paths.revision` does not belong in the key; use `fortifications.version` + permission signature + a diplomacy revision instead of the joined alliance string.

### 10. Entity records are polymorphic; per-tick spreads create short-lived objects per squad
- **Where**: `EntityCollection.ts:48–66` (`Object.assign(record, changes)` adds optional fields lazily), `Simulation.ts:3479` (`{...intent, revision}`), `3523–3534` (`{...motion, speed}`, `{...changes, ...locomotion}`), `FormationLocomotion.ts:229–247` and `338–352` (new `motion`, `intent`, `velocity`, `goal` objects per squad per tick), `AttackApproaches.ts:71` (`new Map(squads.map(...))` per tick), `thinkAi` 4869–4875, `checkWinner` 5428–5432.
- **Severity**: medium under the 384 MB cap. **Confidence**: CONFIRMED allocation sites; GC share SUSPECT (live profile 7.9 %; my probe's heapUsed swings 100 → 350 MB, i.e. the whole reserved-worker budget, which forces more frequent mark-compact than a larger heap would).

### 12. `changeOwner` can silently leave tiles owned by an eliminated faction under raid diplomacy
- **Where**: `Simulation.ts:4814–4816` (early returns: `canCapture(id, owners[tile])`, any building on the tile whose owner `id` cannot capture, wasteland), `5433–5437` (recipient selection checks only `canCapture(beneficiary, victim)`), `5465–5471` (per-tile transfer with no fallback).
- **Severity**: low. **Confidence**: SUSPECT (edge case; not reproduced).
- **Mechanism**: when the victim's tile carries a building owned by a third faction the recipient is not at war with (possible after fallout "surviving edge buildings retain their faction" or stack captures), the second early return skips the tile; `owners[tile]` and `ownedTiles` keep the eliminated id, `player.land` is not decremented, and later squad captures need `declaredWar(claimant, eliminatedId)`, which nothing can establish. This is the same "stale ownership after elimination" class as the 2026-10-15 freeze.
- **Repro sketch**: faction A owns tile t with a port owned by B (captured stack); A is eliminated with beneficiary C at peace with B; assert `owners[t] === 0 || owners[t] === C` after `checkWinner`.

### 13. `attackApproaches.rebuild` and `thinkAi` grouping allocate O(S) structures every tick even with no attackers
- **Where**: `AttackApproaches.ts:60–71` (`loads` rebuilt, `targets = new Map(squads.map(...))`), `Simulation.ts:4869–4875`.
- **Severity**: low. **Confidence**: CONFIRMED.
- **Consequence**: two O(S) Map builds per tick that could be lazy (`targets` is only needed when a group has ≥2 attackers; `armies` grouping could come from `squadIndex.byOwner`).

### 14. 8 Hz vs 10 Hz (design)
- **Where**: `Protocol.ts:18–27`, `LiveMatch.ts:34–35, 714–736`, budgets scaled by `TICKS_PER_SECOND` throughout.
- **Assessment** (CONFIRMED from the handoffs + my probe): per-tick cost is dominated by O(S) movement/combat/capture passes whose cost does not shrink with a longer step, so per-second CPU scales almost linearly with Hz. At the qualification load (S≈1 100, 38 factions, 3 idle humans) the ARM mean tick was 96–104 ms ≈ 0.8 CPU-seconds per second at 8 Hz; at 10 Hz the same code would need ≈1.0 and could not hold 1×. At the 52-faction target my probe reaches S≈1 000 after five simulated minutes at 82 ms on the PC (≈ 200 ms on ARM), so **neither 8 nor 10 Hz holds 1× today**; 8 Hz is the right choice only because it is the cheapest cadence that is still playable, and it buys ~20 % relative to 10 Hz.
- **Responsiveness cost of 8 Hz**: order receipt = up to one 125 ms tick wait + the tick itself + the 200 ms snapshot cadence → the measured 225 ms mean / 400 ms worst receipt. A unit walks 1/8 of its per-second speed per tick, so collision sweeps are coarser (every `clearMovement` and `crossing` already sweeps the full step, so correctness holds) and formation transitions/turn rates are quantised at 125 ms. 10 Hz would shave ~25 ms off mean receipt and ~20 % off the swept distance, which players would not notice; the pace loss under load they would.

## Recommendations (prioritised; "ms" are per-tick estimates at S≈1 500 on ARM, extrapolated from my probe ×2.4 and the handoff phase tables)

1. **Make synchronous repair work budgeted** (Issue 1) — count `LocalDetours` expansions and `clear()` calls into a shared effort meter read by `RouteWork.drain` (pass `read: () => this.paths.work + this.amphibiousPaths.work + this.detourWork`), cap detour expansions per tick (e.g. 1 500) and carry the lattice search across ticks, or route `repair` through `RoutePlanner` as a short-horizon job. Expected: removes the 50–150 ms routing tail (p99), little effect on mean. Effort: 2–3 days incl. a jam fixture test.
2. **Admission backpressure without polling** (Issue 2) — have `RoutePlanner.request` return a reason (`"capacity"`) and let `MovementAdmission` park the admission in a `waitingForCapacity` list that is only revisited when `routePlanner.pendingCount` drops below the class threshold or the admission becomes interactive (controller handover). Reserve a per-player minimum (e.g. 1 background job per AI, 4 per human) inside the 128 instead of a flat 8 for humans. Expected: 5–15 ms mean (the refused-request churn in `drainRouteBatch`), and visibly steadier AI. Effort: 3–4 days; touch `stepAdmissions`, `ShipMovementAdmission.step`, `Trade`/`Armies` callers.
3. **Sleep idle squads in movement** (Issue 5) — maintain an "awake" set: a land squad is awake if it has an intent this tick, moved last tick, is fighting, has a formation transition, a detour, a queued leg, or a hostile within guard radius (cheap `mayContain` test on the hostile partition). Run navigation/locomotion/avoidance/rollback/advanceNavigation only for awake squads; keep the swept guard for awake squads only (stationary vs stationary cannot cross). The `settledFormationLocomotion` fast path is the seed of this. Expected: 30–50 % of movement (15–30 ms) in garrison-heavy late game. Effort: 1 week, needs equivalence tests (checkpoint hash on existing fixtures must stay identical when no squad is asleep-but-affected; design the awake predicate conservatively).
4. **Combat ledger: iterate damaged squads only** (Issue 4) — `for (const id of damage.keys())`, guard `damageManpower` by `dealt > 0`, replace the `filter`/`reverse` passes with a removal list built while applying. Expected: 3–6 ms + measurable GC. Effort: half a day.
5. **AI frontier scan** (Issue 3) — distance check first + early break. Expected: 2–8 ms at 44 AIs. Effort: 1 hour.
6. **Planner bookkeeping** (Issue 6) — keep counters for interactive/background/committed/active jobs updated at insert/retire; sweep deadlines once per second (`tick % 8`); cache `pinSharedPreparation` origins per graph and recompute only when a corridor job starts/ends. Expected: 2–4 ms. Effort: 1–2 days (scheduler checkpoint format unchanged).
7. **Capture key** (Issue 9) — drop `paths.revision` from `environment`; replace the alliance join with a diplomacy revision number. Expected: removes the S-sized refresh bursts (10–20 ms spikes). Effort: 2 hours + extend `IncrementalCapture.test.ts`.
8. **Time-slice elimination transfers** (Issue 7) — mark the faction eliminated immediately but transfer tiles through a budgeted queue (e.g. 2 048 tiles/tick, same shape as `NeutralTerritoryClaims`), and batch `routeFootprints.clear()`/`invalidateCapture` to once per `changeOwner` burst. Expected: turns a 300–800 ms spike into 4–8 ticks of +10 ms. Effort: 2 days; must keep `conquest.beneficiary`/announce semantics and the live-freeze building fix.
9. **Allocation hygiene** (Issue 10/13) — pre-initialise all optional squad fields in `spawnSquad`/`addSquad` (null/undefined) so hidden classes are stable; reuse the `intent` objects (`intents` array of mutable scratch rows keyed by squad like `MotionScratch`); make `AttackApproaches.targets`/`thinkAi` grouping lazy. Expected: 3–8 ms direct + lower GC pause frequency under the 384 MB cap. Effort: 2–3 days, mechanical.
10. **O(B) scans** (Issue 8, afterMovement `buildings.find` per aircraft, `checkWinner` every tick) — use `building(id)`; run `checkWinner` only when a squad/building was removed this tick or a city changed owner (flag set in `removeSquad`/`removeBuilding`/`changeOwner`). Expected: 1–2 ms. Effort: half a day.
11. **Raise the worker heap or shrink residency** — `maxOldGenerationSizeMb: 384` with 100–350 MB live is too tight for 52 factions; either 512–640 MB with 3 concurrent matches on an 8 GB host (fits), or halve `ROUTE_CACHE_TILES` and `START_TREE_CACHE` per graph (three graphs each hold up to 8 MB of cached routes + trees). Effort: config.
12. **Ranked list to get ARM p99 under 125 ms at target load** (expected ms saved on ARM, per tick): (1) repair budgeting −50…−150 tail; (3) idle-squad sleeping −15…−30 mean; (2) admission backpressure −5…−15; (8) sliced elimination −300…−800 on the affected tick; (7) capture key −10…−20 spikes; (4)+(5)+(6)+(9)+(10) −10…−20 mean combined. Together that is the ~35–40 % reduction the handoffs say is missing; without (3) the mean at S≈1 500 stays above 125 ms on this host.
13. **Scalability design beyond that**: the remaining O(S) per-tick passes (formation states, capture row check, combat acquisition, snapshot extraction) should move to a two-tier cadence — "near contact" squads every tick, others every 2–4 ticks with the same deterministic stagger pattern already used by `thinkAi` (`(tick+id)%interval`). Combat LOD by `CombatActivity` epochs already exists for acquisition; extend it to formation facing updates and capture rows. This is the only path to 1 000×1 000 maps with pop-up factions.
